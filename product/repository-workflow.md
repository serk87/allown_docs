# Работа с репозиториями Allown

## Владение кодом

| Локальный каталог | Планируемый репозиторий | Ответственность |
| --- | --- | --- |
| `backend/` | `allown_backend` | API, worker, миграции, API-контракты, инфраструктура сервера |
| `web/` | `allown_web` | React-приложение, прикладная компоновка и клиентская логика |
| `landing/` | `allown_landing` | Публичный сайт, статические страницы, ресурсы и отдельная nginx/Docker-сборка |
| `ui-kit/` | `allown_ui` | `@task-tracker/ui`, общие компоненты, состояния, токены, Storybook |
| `docs/` | `allown_docs` | Требования, планы, рабочие соглашения и решения между репозиториями |
| `mobile/` | Позже | Нативное приложение; отдельная история Git уже существует |

Удалённые репозитории подтверждены: `https://github.com/serk87/allown_backend`, `https://github.com/serk87/allown_web`, `https://github.com/serk87/allown_ui`, `https://github.com/serk87/allown_docs`. Репозиторий лендинга `https://github.com/serk87/allown_landing` создан пользователем; сетевой доступ проверяется при push. Фактические URL устанавливай только по ссылкам пользователя или проверенному списку его репозиториев. При отдельном клонировании сохраняй соседние каталоги `backend`, `web`, `ui-kit`, `landing`, `docs`: web использует `file:../ui-kit`, а Docker-сборка приложения ожидает общий родительский каталог.

## Начало задачи

1. Проверь `git status`, текущую ветку, remote и относящиеся к задаче инструкции в каждом затронутом репозитории. Сохрани чужие и незавершённые изменения, включая staged-файлы.
2. Проследи поведение от интерфейса через API до БД. Определи владельца исправления; изменения контракта согласуй на обеих сторонах.
3. Для новой работы используй отдельную ветку от актуального `dev`; для продолжения задачи сохрани её ветку. Если есть незавершённые изменения, сначала определи их происхождение, затем выбирай checkout или изоляцию. Не переименовывай существующие ветки и не переписывай историю ради единообразия.
4. При подключении remote проверь владельца, видимость и существующую историю. Сохрани локальную историю. Для непустого remote сравни истории до отправки; force-push и замена удалённой истории требуют прямого поручения пользователя.

## Проверки и коммиты

- Регрессию воспроизведи до исправления; тест должен проверять наблюдаемое поведение. Команды проверок бери из текущих manifests и инструкций репозитория.
- Отдельно проверяй типы, тесты и production-сборку: успешные тесты не доказывают успешную сборку. Ошибку первой команды нельзя скрывать exit code последней команды в shell.
- Для авторизации проверяй два разных аккаунта, отсутствие доступа к чужим данным, новый и повторный вход. Для пользовательского текста проверяй кириллицу, латиницу и смешанные названия.
- Разделяй новые и прежние падения тестов подтверждённым сравнением. В отчёте перечисляй оставшиеся падения и ограничения; неполный набор не называй полностью прошедшим.
- Коммит объединяет одну понятную задачу. До staging просмотри diff и список untracked; добавляй явные пути. Проверь staged diff, включая ранее подготовленные изменения пользователя. Перед первой загрузкой проверь также историю на секреты и большие служебные файлы; выводи только имена файлов с подозрениями, не значения секретов.
- В Git хранятся исходники, lockfiles, миграции, тесты и инструкции. Секреты, `.env` с реальными значениями, дампы, cookies, `node_modules`, кэш и сборочные каталоги остаются вне Git. Примеры конфигурации содержат заглушки.
- Сохраняй версии и changelog по текущим правилам проекта; не выдумывай sprint/task ID. Для задачи без ID используй понятный `fix:`, `feat:`, `docs:` или `chore:`.
- Просьба пользователя загрузить изменения разрешает необходимые коммиты и push этих изменений. Она сама по себе не означает слияние незавершённых веток в `main`. Обычно изменения идут через PR в `dev`; `main` — принятые релизы.
- При первой загрузке отдельно сохрани действующий рабочий снимок и существующие ветки. Подтверждай push сравнением локального и удалённого SHA. Не объявляй ветку проверенным релизом при известных падениях.

## Изменения между репозиториями

Общий UI сначала меняется в `allown_ui`, затем подключается в web. Перед выбором компонента читай каталог пакета. Новые и затронутые контролы используют экспортируемые компоненты, импорт стилей и `.tt-theme`; правила провайдерских кнопок сохраняются.

API-контракт принадлежит backend. Изменяя DTO или обязательность поля, проверь клиентский парсер, типы и состояние UI. Связанные PR и SHA указывай в описании выпуска. Сборка из чистых checkout должна воспроизводить набор версий без непереданных локальных файлов.

## Выпуск

1. Проверь фактическое окружение по конфигурации и инвентаризации. Текущий домен — `allown.ru`, приложение — `/app/`, каталог приложения на сервере — `/srv/task-tracker`.
2. Перед сборкой проверь свободное место и inode на файловых системах Docker и БД. При свободном месте менее 5 ГБ сначала оцени размер сборки и освободи восстановимые ресурсы приложения или согласуй увеличение диска; после сборки и после запуска повтори проверку. Не удаляй данные, тома или ресурсы других приложений для освобождения места.
3. Формируй релиз из проверенных версий всех зависимостей. При передаче отдельных файлов сверяй полный diff: entrypoint, импорт CSS UI kit, конфигурация и миграции также входят в релиз. Предпочитай сборку из checkout конкретных SHA.
4. Перед изменением схемы или разрешённой очисткой сохрани проверенную резервную копию. Изменения схемы выполняй миграциями; сохраняй применённые миграции неизменными. Очистка пользовательских данных допускается только по прямому запросу пользователя и не повторяется в следующих задачах автоматически.
5. Обновляй только сервисы Allown, необходимые для задачи. Dev-сессии и demo seed должны быть выключены в опубликованном окружении. Запиши версии, способ восстановления и результат health checks.
6. Проверь именно опубликованную сборку: ответы API, интерфейс, фактически применённые стили, основной сценарий и ошибки. Локальная проверка не заменяет проверку релиза. Используй отдельные тестовые данные; после проверки удаляй только созданные тобой записи и временные сессии.
7. Завершай отчётом: что изменено, где опубликовано, что проверено и что осталось нерешённым. Отдельно указывай commit/push/deploy: одно не доказывает другое.

## Ведение проекта

Храни требования и решения в `allown_docs`, работу над конкретным компонентом — в Issues его репозитория. В задаче указывай проблему, ожидаемое поведение, критерии проверки и связанные репозитории. По завершении связывай задачу с PR/коммитами и результатами проверки. Не закрывай задачу как выполненную, пока её критерии не подтверждены.

Аналитика получает только обезличенные события и технические метрики. Названия пространств, проектов, задач, описания, комментарии и данные авторизации в аналитику не отправляются.
